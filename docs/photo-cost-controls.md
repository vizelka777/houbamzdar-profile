# Фотографии без Bunny Optimizer и пауза автоматической AI-проверки

## Настройки backend

- `CAPTURE_IMAGE_VARIANTS_ENABLED=true`: при загрузке Go создаёт JPEG-копии для карты, галереи, всплывающего окна и большого просмотра. Размер по длинной стороне: 128, 640, 960 и 1600 пикселей. Файлы лежат в `<original-key>.variants-v1/<variant>.jpg`. Оригинал не меняется. Удаление фотографии удаляет и её копии.
- `CAPTURE_AI_VALIDATION_DISABLED=true`: публикация пропускает автоматическое распознавание грибов. Проверки авторизации, права публикации, наличия GPS и положения в Чехии продолжают работать.

У публикаций без AI статус `approved_without_ai`; фиктивный положительный AI-результат не записывается. Вид гриба автоматически не определяется. Существующие результаты распознавания сохраняются. Ручная AI-перепроверка модератором доступна и при запуске может расходовать средства на Gemini.

Без первой настройки API отдаёт исходные фотографии; новый frontend не обращается к Optimizer ни в одном режиме. Без второй настройки автоматическая AI-проверка включена. Некорректное значение второй настройки также не отключает проверку.

## Вернуть автоматическую проверку

В настройках backend Magic Container изменить **только**:

```text
CAPTURE_AI_VALIDATION_DISABLED=false
```

Применить обновление контейнера, сохранив существующие `CAPTURE_AI_VALIDATOR_URL`, `CAPTURE_AI_VALIDATOR_TOKEN` и настройки моделей Edge Script. Пересборка кода и включение Bunny Optimizer не нужны: backend готовит JPEG до 384 пикселей с качеством 70 и передаёт его в существующий validator inline. При недоступной подготовке сохранён прежний fallback чтения оригинала самим validator.

Проверка применяется к новым запросам публикации. Уже опубликованные во время паузы фотографии не перепроверяются автоматически. Если такой снимок снять с публикации и отправить снова после включения проверки, он попадёт в очередь проверки. Ранее отклонённые или завершившиеся ошибкой запросы сами не перезапускаются.

## Первый переход

1. Прочитать `docs/bunny-deploy.md` и `docs/bunny-deploy-incidents.md`.
2. Взять текущие storage-настройки из live app; для чтения списка фотографий использовать read-only DB token из `docs/bunny-db-access.md`.
3. `go run ./cmd/backfillvariants` покажет число фотографий без записи файлов или строк БД.
4. `go run ./cmd/backfillvariants --apply --workers 4` подготовит копии старых фотографий. Оригиналы и БД не изменяются. Повторный запуск пропускает завершённые наборы; `lightbox.jpg` записывается последним. Команда прекращает работу после десяти ошибок. Bunny Storage не поддерживает HEAD в этом потоке: наличие копии проверяется GET с Range.
5. Развернуть backend с обоими флагами `true`. Повторить backfill, чтобы покрыть фотографии, загруженные во время первого прохода старым backend.
6. Проверить ссылки `image_variants` из API. Загрузить новый `app.js`, `server-storage.js`, `sw.js`; очистить CDN-кеш сайта. Версия PWA-кеша должна обновиться.
7. После успешных проверок отключить **OptimizerEnabled** именно у pull zone `foto.houbamzdar.cz`. Storage, CDN, домены и Edge Script остаются.

## Проверки

`go test ./...`, `node web-static/capture-images.test.cjs`, `node --check web-static/app.js`, `node --check web-static/server-storage.js`, `node --check web-static/sw.js`.

После выката проверить `/health`, `/api/session`, `/api/public/posts`, `/api/public/captures`, размеры/доступность копий из `image_variants`, отсутствие запросов Optimizer в новом frontend и фактическое `OptimizerEnabled=false` у фото-зоны.

Если нужно отключить использование готовых копий, установить `CAPTURE_IMAGE_VARIANTS_ENABLED=false`: frontend будет использовать оригиналы. Копии при этом сохраняются. При нормальной эксплуатации оставлять настройку включённой, в том числе для удаления копий вместе с фотографией.
